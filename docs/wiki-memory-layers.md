# 同一 Talker 的共享 Wiki 与四层记忆

共享范围：Hinter 选择的 Talker。Hinter 在该 Talker 的任一会话写入提示或封禁后，其全部会话（含新会话）共用这套 Wiki；其他 Talker 隔离。服务器依据空间的 owner_user_id 解析范围，不根据前端文字、话题或模型推断身份。未绑定的旧空间只在该旧空间内生效，不能把所有空 owner 合并成一个用户。

| 记忆层 | 来源 | 执行方式 |
| --- | --- | --- |
| 长期记忆 | 该 Talker 的 Wiki、允许披露的 Hint、个人背景 | DeerFlow 原生 MemoryManager 注入；公开提示原则置前，事实按相关性召回；recall_memory 继续读取同一存储 |
| 短期记忆 | 当前会话最近的公开、未撤回记录 | 每轮按时间和修订构建上下文，限制大小 |
| 当轮记忆 | 当前请求、语言判定、关联的人工补充 | 明确本轮对象、语言和来源，续答关联原始问题 |
| 封禁记忆 | Hint 明确封禁指令、管理员的回答限制表单 | 独立服务端控制，不依赖模型是否召回，也不向用户披露私有指令 |

## 实现

- `employee/wiki.py` 原子归档 Hint。`employee/answer_policy.py` 将明确的中文/英文“禁止回答某主题”指令同步成封禁文档；主题名称由文本提取，没有写死某个产品。相同 Talker、相同主题合并来源。旧 Hint 可以幂等补录。
- 控制文档复用 MySQL 的 versioned memory_documents，标记 origin=answer_policy、memory_layer=prohibition、scope=talker。原文和来源保持私有，所有者以关联空间实时解析。普通记忆编辑接口禁止修改控制文档，管理员专用接口检查 guidance.write 和版本。
- `memory_context.py` 统一标明四层上下文；长期数据继续由 DeerFlow 原生记忆中间件注入，不重复拼入提示。`MySQLMemoryManager` 严格按 Talker owner 过滤；查询词不影响公开提示原则的置前注入。
- 提交入口先记录是否命中封禁，命中不播“我查一下”。Worker 在主模型调用前判断；原生授权、工具调用、流式文本发布和最终入库再检查。被拦截时仅按原请求语言给简短拒答，不搜索、不请求 Hinter 补充、不生成问题投影。
- 提交时已命中的封禁在同一事务中直接保存用户输入及拒答记录，Run 正常完成，不进入 Agent 队列。中文提示为“我暂时无法回答这个问题，可以换一个问题提问。”；响应带回规范输入/助手记录以立即显示，语音通话沿用正式回答 TTS。执行期间新增封禁仍由 worker 的后续检查生成正常拒答。
- 明确的英文/中文主题、空格/大小写/标点变体及管理员提供的别名参与匹配；英文名称含数字时增加数字读法别名。简单“它/its/继续”等后续沿用上一条受限用户请求的主题。用户自造全新代称不能仅靠字面规则保证覆盖，管理员可追加别名；没有声称提供通用的语义安全证明。
- 每次检查读取当前启用的控制。来源撤回、改成别的主题后旧来源不继续支持原封禁；手动停用有版本检查。历史已披露文本不删除，受限文本不再通过朗读接口生成新音频。

## Hint 界面

“Hinter 提示与备注”仍保留原文与披露选择。明确的禁止回答指令无需公开原文，也会进入该 Talker 的共享封禁记忆；其他私有事实继续仅管理员可见。允许披露的 Hint 在同一 Talker 的全部会话召回。

新增“回答限制”展示当前 Talker 的生效规则，支持输入主题/别名及启用、停用。范围固定为所选 Talker 的全部会话，不提供跨 Talker 的全局开关。保存 Hint 后刷新此列表；规则控制与普通 Wiki 编辑分开，避免把事实可见性误当成执行权限。

主题输入支持名称或完整封禁指令；服务端统一提取主题。历史规则规范化不更换规则 ID、不重置手动停用，也不扩大 Talker 范围。原有失败请求仅在仍被当前规则限制时，才由运维恢复成有正常拒答记录的已完成状态，旧失败事件保留用于追溯。
